# 設計判断と実装の落とし穴

なぜこの作りなのか、と、実際に踏んだ罠。**同じ穴を掘り直さないための記録。**

データ側の実測値は [DATA.md](DATA.md)、使い方は [README](../README.md)。

## 設計上の決めごと

- **日別の区切りは JST。** basetime は UTC だが観測時刻は JST で配信される。
  日本の落雷を日単位で見るのは JST が自然なので、アーカイブとタイルは JST 日付で切る。
  1つの JST 日は UTC 15:00(前日)〜15:00 の basetime にまたがる。
  - スライスの枠番は「JST 00:05 終端 = 枠0」「翌 00:00 終端 = 枠287」と定義し、
    日 D の枠 0..287 が obstime `(D 00:00, D+1 00:00]` をちょうど覆うようにしている。
  - **features の日付は常に obstime が決める。** 境界の一瞬（obstime がちょうど
    `00:00:00.000`）だけ、枠のカバレッジと1件だけ食い違う余地がある。実害はないが仕様。
- **配信元の `id` を一次キーにしない。** `nowc_<basetime>_<validtime>_liden_<連番>` の
  連番はスライス内の並び順に依存する。時刻・位置・種別を一次情報として持たせ、
  `src_id` は出所と重複排除のためだけに残す。
- **`epoch_ms` を持たせる。** MapLibre の filter は数値比較が軽く、時間スライダーに
  そのまま使える。文字列の時刻だけだと絞り込みが書きづらい。
- **最大ズームは 7。** 元データの座標精度が 0.001 度なので、タイル解像度が
  精度に達する ZL は `360/(4096×2^z) ≤ 0.001` → `z ≥ 6.5` → **z7**。
  それ以上は情報を増やさず、同じ点を多くのタイルに複製するだけ。実測（2026-08-21・
  20,271件）:

  | 最大ZL | PMTiles サイズ | 最大ZLの一意 `src_id` |
  |---:|---:|---:|
  | 6 | 2.12 MB | — |
  | **7** | **2.71 MB** | **20,271** |
  | 8 | 3.34 MB | — |
  | 10 | 4.75 MB | — |
  | 12 | 6.68 MB | 20,271 |

  z7 と z12 で最大ZLの一意 `src_id` が **完全一致**（どちらも欠落なし）。
  容量は 59% 減る。高ズームはビューア側のオーバーズームで描く。
- **`-r1` で点の間引きを止める。** 落雷は1点1事象なので落とさない。低ZLの過密だけ
  `--drop-densest-as-needed` に任せる（見た目の問題で、最大ZLの件数には影響しない）。
- **内容が変わらなければアーカイブを書かない。** 書き直すと mtime が動き、
  `build.py` が「入力が新しい」と見て全日のタイルを作り直す。`write_archive()` が
  バイト列を比較して `SAME` を返す。
  - バイト列を一致させるには **`mtime=0` だけでは足りない。**
    `gzip.GzipFile(fileobj=開いたファイル)` は fileobj の `.name` を gzip ヘッダの
    FNAME に埋めるので、同じ内容でもバイト列が変わる。`io.BytesIO` に書けば付かない。

## パイプライン

```
data/raw/YYYY/MM/DD/liden_<basetime>.json   ← collect.py    5分スライス（キャッシュ・gitignore）
archive/liden_YYYYMMDD.geojson.gz           ← normalize.py  JST日別の恒久アーカイブ（コミット）
archive/manifest.json                       ← normalize.py  288枠のカバレッジ
dist/liden_YYYYMMDD.pmtiles + index.json    ← build.py      ベクタータイル（gitignore）
```

コマンドの使い方は [README](../README.md#使い方) を参照。

### 空スライスも保存する

雷が無かった5分も `{"type":"FeatureCollection","features":[]}` として保存する。
**「取得済みで雷なし」と「未取得」を区別できないとカバレッジが検証できない。**
初回の4日ぶん1,153スライスのうち87スライスが空だった。

404（配信終了）は `.miss` マーカーを残し、以後試行しない。

### カバレッジの見方

`status.py` は5つに分ける。**まだ取れるものと、もう取れないものを混ぜない**のが要点。

```
JST 日付      取得済    欠落    窓外  期限切  配信終    合計   落雷件数
2026-08-19       148     140       0       0       0     288      1,256
2026-08-20       288       0       0       0       0     288     17,055
2026-08-21       288       0       0       0       0     288     23,639
```

| 区分 | 意味 |
|---|---|
| 取得済 | `manifest.json` のカバレッジに立っている（空スライス含む） |
| 欠落 | 収集窓の中で未取得 → `collect.py` をそのまま回せば埋まる |
| 窓外 | 収集窓より古いが配信保持期間の中 → `--window-days 5` で **まだ取れる** |
| 期限切 | 配信保持期間より古く未取得 → **もう取れない** |
| 配信終 | 404 を確認済み |

判定は `data/raw/` の有無ではなく **`manifest.json` のカバレッジ**を見る。
raw はいつ消してもよいキャッシュなので、raw を基準にすると掃除した瞬間に
「欠落」が復活してしまう。

## 実行環境

- Python 3.12（標準ライブラリのみ。収集・正規化に外部パッケージは不要）
- tippecanoe 2.80 / pmtiles 1.30（タイル生成のみ）
- Node.js 20+（ビューアのみ）

### tippecanoe が WSL 側にしか無い場合

`build.py` は自動で切り替える:

1. PATH に `tippecanoe` があればそのまま実行（Linux・CI・WSL 内）
2. 無ければ `wsl.exe` 経由で実行し、パスを WSL 形式に変換して渡す

パス変換はリポジトリ直下を一度だけ `wslpath` で引いて相対パスを繋ぐ。
`/mnt/c` 固定を前提にしない。

### tippecanoe は `.pmtiles` を指定しても mbtiles を書く

2.80 で確認（先頭バイトが `SQLite format 3`）。`build.py` は出力の
**マジックバイトを見て判定**し、SQLite なら `pmtiles convert` を通す。
既に PMTiles ならそのまま使う。バージョンによって挙動が違うので、
拡張子でもバージョン番号でもなく中身で判断する。

## ビューア実装で踏んだこと

- **`['literal', '#ffc247']` を色として渡さない。** `literal` は配列・オブジェクト
  専用なので色式として不正で、**レイヤーの paint が丸ごと無効になる**。しかも
  `map.on('error')` に何も出ず、`console.error` にも出ない。症状は
  「点は薄く出るが背景地図が真っ白」という一見無関係な壊れ方だった。
  経過時間で色を分けないときは **素の色文字列**を返す。
- **`queryRenderedFeatures` はタイル読み込み前は空を返す。** `setFilter` の直後に
  数えると常に 0 件になる。`map.on('idle')` で数え直す。
- **`queryRenderedFeatures` は同じ点をタイル境界で二重に返す。** 件数は `src_id` で
  数え直す（実測: 生の配列 21,412 に対し一意 20,271）。
- **背景地図が `pmtiles://` なので、`maplibregl.addProtocol('pmtiles', ...)` は
  落雷タイルと無関係に必須。** 外すと背景が出ない。
- ビューアを変えたら実際に描画とクリック読み取りを確認する。タイルURLや式の不整合は
  「地図は出るがオーバーレイだけ出ない」形で静かに壊れる。
