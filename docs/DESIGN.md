# 設計判断と実装の落とし穴

なぜこの作りなのか、と、実際に踏んだ罠。**同じ穴を掘り直さないための記録。**

データ側の実測値は [DATA.md](DATA.md)、使い方は [README](../README.md)。

## 設計上の決めごと

- **日別の区切りは JST。** basetime は UTC だが観測時刻は JST で配信される。
  日本の落雷を日単位で見るのは JST が自然なので、アーカイブとタイルは JST 日付で切る。
  1つの JST 日は UTC 15:00(前日)〜15:00 の basetime にまたがる。
  - スライスの枠番は「JST 00:05 終端 = 枠0」「翌 00:00 終端 = 枠287」と定義し、
    日 D の枠 0..287 が obstime `(D 00:00, D+1 00:00]` をちょうど覆うようにしている。
  - **features の日付は常に obstime が決める。** 境界の一瞬（obstime がちょうど
    `00:00:00.000`）だけ、枠のカバレッジと1件だけ食い違う余地がある。実害はないが仕様。
- **配信元の `id` を一次キーにしない。** `nowc_<basetime>_<validtime>_liden_<連番>` の
  連番はスライス内の並び順に依存する。時刻・位置・種別を一次情報として持たせ、
  `src_id` は出所と重複排除のためだけに残す。
- **`epoch_ms` を持たせる。** MapLibre の filter は数値比較が軽く、時間スライダーに
  そのまま使える。文字列の時刻だけだと絞り込みが書きづらい。
- **最大ズームは 7。** 元データの座標精度が 0.001 度なので、タイル解像度が
  精度に達する ZL は `360/(4096×2^z) ≤ 0.001` → `z ≥ 6.5` → **z7**。
  それ以上は情報を増やさず、同じ点を多くのタイルに複製するだけ。実測（2026-08-21・
  20,271件）:

  | 最大ZL | PMTiles サイズ | 最大ZLの一意 `src_id` |
  |---:|---:|---:|
  | 6 | 2.12 MB | — |
  | **7** | **2.71 MB** | **20,271** |
  | 8 | 3.34 MB | — |
  | 10 | 4.75 MB | — |
  | 12 | 6.68 MB | 20,271 |

  z7 と z12 で最大ZLの一意 `src_id` が **完全一致**（どちらも欠落なし）。
  容量は 59% 減る。高ズームはビューア側のオーバーズームで描く。
- **`-r1` で点の間引きを止める。** 落雷は1点1事象なので落とさない。低ZLの過密だけ
  `--drop-densest-as-needed` に任せる（見た目の問題で、最大ZLの件数には影響しない）。
- **内容が変わらなければアーカイブを書かない。** 書き直すと mtime が動き、
  `build.py` が「入力が新しい」と見て全日のタイルを作り直す。`write_archive()` が
  バイト列を比較して `SAME` を返す。
  - バイト列を一致させるには **`mtime=0` だけでは足りない。**
    `gzip.GzipFile(fileobj=開いたファイル)` は fileobj の `.name` を gzip ヘッダの
    FNAME に埋めるので、同じ内容でもバイト列が変わる。`io.BytesIO` に書けば付かない。

## パイプライン

```
data/raw/YYYY/MM/DD/liden_<basetime>.json   ← collect.py    5分スライス（キャッシュ・gitignore）
archive/liden_YYYYMMDD.geojson.gz           ← normalize.py  JST日別の恒久アーカイブ（コミット）
archive/manifest.json                       ← normalize.py  288枠のカバレッジ
dist/liden_YYYYMMDD.pmtiles + index.json    ← build.py      ベクタータイル（gitignore）
```

コマンドの使い方は [README](../README.md#使い方) を参照。

### 空スライスも保存する

雷が無かった5分も `{"type":"FeatureCollection","features":[]}` として保存する。
**「取得済みで雷なし」と「未取得」を区別できないとカバレッジが検証できない。**
初回の4日ぶん1,153スライスのうち87スライスが空だった。

404（配信終了）は `.miss` マーカーを残し、以後試行しない。

### カバレッジの見方

`status.py` は5つに分ける。**まだ取れるものと、もう取れないものを混ぜない**のが要点。

```
JST 日付      取得済    欠落    窓外  期限切  配信終    合計   落雷件数
2026-08-19       148     140       0       0       0     288      1,256
2026-08-20       288       0       0       0       0     288     17,055
2026-08-21       288       0       0       0       0     288     23,639
```

| 区分 | 意味 |
|---|---|
| 取得済 | `manifest.json` のカバレッジに立っている（空スライス含む） |
| 欠落 | 収集窓の中で未取得 → `collect.py` をそのまま回せば埋まる |
| 窓外 | 収集窓より古いが配信保持期間の中 → `--window-days 5` で **まだ取れる** |
| 期限切 | 配信保持期間より古く未取得 → **もう取れない** |
| 配信終 | 404 を確認済み |

判定は `data/raw/` の有無ではなく **`manifest.json` のカバレッジ**を見る。
raw はいつ消してもよいキャッシュなので、raw を基準にすると掃除した瞬間に
「欠落」が復活してしまう。

## 実行環境

- Python 3.12（標準ライブラリのみ。収集・正規化に外部パッケージは不要）
- tippecanoe 2.80 / pmtiles 1.30（タイル生成のみ）
- Node.js 20+（ビューアのみ）

### tippecanoe が WSL 側にしか無い場合

`build.py` は自動で切り替える:

1. PATH に `tippecanoe` があればそのまま実行（Linux・CI・WSL 内）
2. 無ければ `wsl.exe` 経由で実行し、パスを WSL 形式に変換して渡す

パス変換はリポジトリ直下を一度だけ `wslpath` で引いて相対パスを繋ぐ。
`/mnt/c` 固定を前提にしない。

### `@types/node` は依存に明示する

`viewer/vite.config.ts` は `node:fs` / `node:path` / `node:url` を使うので
`@types/node` が要る。**これを宣言していなくてもローカルでは通ってしまう** ——
TypeScript は親ディレクトリを遡って `node_modules/@types` を探すため、
ホームディレクトリの無関係なインストール（`~/node_modules/@types/node`）を
拾っていた。CI にはそれが無いので `TS2307: Cannot find module 'node:fs'` で
落ちる（実際に踏んだ。`tsc --listFiles` で参照元を確認できる）。

`devDependencies` に `@types/node` を入れ、`tsconfig.json` の `types` にも
`"node"` を明示してある。**「ローカルで通る」は依存が宣言されている証拠に
ならない。**

### tippecanoe のバージョンはローカルと CI で違う

ローカル（WSL）は **v2.80.0** だが、これは `main` からのビルドで
**`2.80.0` というタグは存在しない**（`felt/tippecanoe` の最新リリースタグは
`2.79.0`）。CI で `-b 2.80.0` を指定すると
`fatal: Remote branch 2.80.0 not found in upstream origin` で落ちる（実際に踏んだ）。

CI は `2.79.0` を固定でビルドする。**バージョン差は問題にならない**——
`build.py` は出力の中身（マジックバイト）で mbtiles / PMTiles を判定するので、
どちらの挙動でも通る。

### tippecanoe は `.pmtiles` を指定しても mbtiles を書く

2.80 で確認（先頭バイトが `SQLite format 3`）。`build.py` は出力の
**マジックバイトを見て判定**し、SQLite なら `pmtiles convert` を通す。
既に PMTiles ならそのまま使う。バージョンによって挙動が違うので、
拡張子でもバージョン番号でもなく中身で判断する。

## パネルは画面左端に貼り付ける

**浮きカードにしない。** `top:16px / left:16px / border-radius:16px` の
フローティングパネルは、地図の左上——ちょうど見たいところ——を余白で削るだけで
得がない。左端に貼り付いた全高サイドバーにする。

- `top:0; left:0; bottom:0; border-radius:0; border-right`。**`height:100dvh` に
  頼らず `top:0` + `bottom:0`** で縦いっぱいにする（`height:auto` だと内容が
  画面より低いときパネルが縮み、切替で下端が動く）
- **`backdrop-filter`（すりガラス）は使わない。** 実GPUでの合成不具合により、
  内部スクロールを持つパネルで描画が破綻することがある
- 畳むときは `.panel.collapsed` を付けて `bottom:auto; height:auto` に戻す。
  **`hidden` だけだと中身が消えた全高の板が残る**（実際に踏んだ）
- 狭い画面（`max-width:640px`）は画面端まで使うボトムシート
  （`left:0; right:0; bottom:0; max-height:62dvh; border-radius:0`）。
  ここで `.panel.collapsed { bottom: 0 }` を **明示的に打ち消す**必要がある。
  モバイルは `top:auto` なので、デスクトップ用の `bottom:auto` が効くと
  パネルが画面最上部へ飛ぶ

構成は姉妹リポジトリ
[`jartic-traffic-signal-cycle-converter`](https://github.com/shiwaku/jartic-traffic-signal-cycle-converter)
の `viewer/src/style.css` に合わせている。
（`railway-frequency-converter` 側は浮きカードなので、そちらから CSS を
流用すると余白が付いてくる。**最初それで作ってしまった。**）

## 発光表現と再生の作り

姉妹リポジトリ
[`jartic-traffic-signal-cycle-converter`](https://github.com/shiwaku/jartic-traffic-signal-cycle-converter)
の `viewer/src/map/layers/signal.ts` に構成を合わせている。

- **ぼかした円を3層重ねる。** 1枚の円に blur を掛けただけでは「光」に見えない。

  | 層 | `circle-radius`（ZL3→7→12） | `circle-blur` | 不透明度の基準 | 色 |
  |---|---|---:|---:|---|
  | `liden-glow` | 11 → 18 → 36 | 2.5 | 0.5 | 経過時間 |
  | `liden-mid` | 5.5 → 9 → 17 | 1.5 | 0.8 | 経過時間 |
  | `liden-core` | 2 → 3 → 5 | 0 | 1.0 | 白（ダーク時） |

  `circle-blur` は **1 を超えてよい**。2.5 で外周まで大きくにじむ。
- **半径は低ズーム側を持ち上げた曲線にする。** 全体を一律に倍しても全国表示
  （ZL4〜5）ではほとんど変わらない。同じ絵で倍率だけ変えて実測すると、
  2.4倍にしても画面の明るさ合計は 72.9M → 74.8M（+2.5%）しか動かない。
  効くのは **ZL3 側の値**。
  ただし上げすぎると暈が融合して密集部が1つの塊になり、個々の落雷が消える
  （ZL3 で glow=14 まで上げたら瀬戸内が一塊になった）。11 が上限に近い。
- **芯を白にするのはダークのときだけ。** ライトの淡色地図では白い芯が背景に溶けて、
  落雷が光って見えない。ライトでは芯にも経過時間の色を載せる。
- **既定テーマはダーク。** 発光が主役の可視化なので OS 設定より優先する
  （`theme.ts`）。一度切り替えたら localStorage の選択を尊重する。
- **配色は明度差より色相差。** ぼかした小さな発光点では明度差はにじんで潰れるので、
  白→黄→橙→赤紫と色相を回す（姉妹リポジトリの `docs/design.md` に同じ結論の実測メモがある）。
- **時刻カーソルは分単位。配信スライスの5分単位と混ぜない。**
  `epoch_ms` はミリ秒まで持っているので、表示の時間解像度を5分に縛る理由がない。
  当初カーソルを5分枠で持っていたため、「1分/コマ」を足しても
  `round(1/5) = 0` → 最低1枠に丸められて「5分/コマ」と同じ動きになった。
  **5分という単位はカバレッジ（288枠）の話で、表示解像度とは別物。**
- **再生ループで `setFilter` を触らない。** フィルタを差し替えるとタイルが再評価されて
  重くなる。時刻の窓は **`circle-opacity` の式で窓の外を 0 にして**表現し、
  `setFilter` は放電種別の切替（頻度が低い）だけに使う。
  - 副作用として、**不透明度0で消した点も `queryRenderedFeatures` は返す。**
    可視件数は JS 側で `epoch_ms` を見て数え直す必要がある。
  - 当たり判定は `liden-glow`（いちばん大きい）、件数は `liden-core`（芯なので
    画面端で余分に拾わない）と、層を使い分けている。

## ビューア実装で踏んだこと

- **`['literal', '#ffc247']` を色として渡さない。** `literal` は配列・オブジェクト
  専用なので色式として不正で、**レイヤーの paint が丸ごと無効になる**。しかも
  `map.on('error')` に何も出ず、`console.error` にも出ない。症状は
  「点は薄く出るが背景地図が真っ白」という一見無関係な壊れ方だった。
  経過時間で色を分けないときは **素の色文字列**を返す。
- **`queryRenderedFeatures` はタイル読み込み前は空を返す。** `setFilter` の直後に
  数えると常に 0 件になる。`map.on('idle')` で数え直す。
- **`queryRenderedFeatures` は同じ点をタイル境界で二重に返す。** 件数は `src_id` で
  数え直す（実測: 生の配列 21,412 に対し一意 20,271）。
- **背景地図が `pmtiles://` なので、`maplibregl.addProtocol('pmtiles', ...)` は
  落雷タイルと無関係に必須。** 外すと背景が出ない。
- ビューアを変えたら実際に描画とクリック読み取りを確認する。タイルURLや式の不整合は
  「地図は出るがオーバーレイだけ出ない」形で静かに壊れる。

## タイムラインは5日通しで、日は「レーン」として詰める

日ごとにタブを押し直すのが面倒だったので、時刻カーソルを1日ぶんではなく
**表示している全日を通した値**にした（`state.minute` は 0..日数×1440）。

- **実時間ではなく日の枚数で数える。** 収集していない日はそもそも
  `index.json` に載らないので、アーカイブには穴が空きうる。実時間で測ると
  誰もいない何日ぶんもスクラブする羽目になる。1日＝1レーンとして詰めれば
  空白を飛ばせる。**代わりに日付は時計にも目盛りにも必ず出す**（時刻だけ
  出すと、詰めたぶん何日目か分からなくなる）。
- **真夜中でタイルを貼り替える。** タイルは日ごとなので `syncDay()` が
  カーソルの乗っているレーンを見てソースを差し替える。毎コマ呼ばれるので、
  日が変わっていなければ即戻ること（`addLidenLayers` はソースの作り直し）。
- **自動で日が変わるときは `fitBounds` しない。** 通し再生で真夜中を越える
  たびに地図が飛ぶ。画面を合わせるのは日付タブを押したとき（`jumpToDay`）だけ。
- **日が変わっても `activeTypes` を作り直さない。** 日によって出る type は
  違うが、真夜中ごとに絞り込みが戻ると、消したはずの雲放電が勝手に復活する。
  起動時に**全日の type の和**で初期化しておく。
- **種別トグルの件数も全日合計にする。** 日ごとの件数にすると、通し再生で
  真夜中を越えるたび数字が飛んで、自分が絞ったのかデータが変わったのか
  分からなくなる。
- **目盛りは `space-between` では合わない。** 5個並べると最初が左端・最後が
  右端（i/4 の位置）になるが、日付のあるべき位置は 1日＝1レーンなので i/5。
  そのままだと**目盛りと中身が最大1日ぶんずれる**。等幅の列に切って左寄せにする。

### 真夜中で「一瞬消える」の正体は2つある

最初の実装では真夜中でぱっと画面が空になった。原因は別々の2つで、片方だけ
直しても消えない。

1. **タイルの差し替え待ち。** 「消す→足す→読み終わるまで空」。
2. **残光が前日のタイルに届かない。** 00:00 のとき残光30分の窓は 23:30〜00:00
   ＝**全部前日**。新しい日のタイルしか載っていなければ描くものが無い。
   5分/コマなら 30分ぶん＝6コマ＝0.7秒くらい空くので「一瞬消える」に見える。

実測（8/26→8/27、残光30分、件数表示）:

| 時刻 | 直す前 | 直した後 |
|---|---:|---:|
| 23:55 | 1,500 | 1,500 |
| **00:00** | **0** | **1,506** |
| 00:15 | 251 | 985 |
| 00:30 | 531 | 531 |

直しかたは**スロット2枚（表と裏）**:

- **裏で読み終わってから表に昇格させる。** `removeLidenLayers` を先にやらない。
  レイヤー id は基底名＋スロット（`liden-core-a`）で、2日ぶんを同時に載せられる。
- **境界の 120分前（シミュレーション時間）から次の日を裏へ積む。**
  早すぎると、昇格直後の裏に残っている**前日**を追い出してしまう。
  その前日が 2. の残光を描いているので、追い出すと元の症状に戻る。
- **時刻窓に掛かるスロットは全部塗る。** 表だけ塗ると 2. が直らない。
  経過時間の色も不透明度も `epoch_ms` から決まるので、両方に同じ paint を
  流し込めばそのまま繋がる。
- **件数もクリックも「塗っているスロット全部」に合わせる。** 表だけ見ると
  真夜中の件数が実際より少なく出る。
- `whenSourceLoaded` には**保険のタイムアウト**を入れる。`sourcedata` が
  期待どおり飛ばない日（タイルが1枚も無いなど）で固まらせない。最悪でも
  元の「一瞬消える」に戻るだけ。

### `queryRenderedFeatures` は不透明度0の点も返す

クリックの当たり判定でも踏んだ。15:00（残光3時間＝12:00〜15:00）を見ているのに
**17:45 の落雷**の内容がツールチップに出た。`queryRenderedFeatures` は
「タイルに載っていて描画対象」なら不透明度0でも返すため、先頭をそのまま採ると
光っていない点を拾う。**時刻窓で絞ってから、いちばん新しい（＝いちばん明るい）
ものを選ぶ**こと。件数を数えるほうには元から同じ注意書きがあったが、
クリック側が漏れていた。

### レイヤー id を固定してイベントを張らない

`map.on('click', PICK_LAYER, ...)` のようにレイヤー指定で張ると、真夜中で
スロットが入れ替わった側では拾えなくなる。地図全体で受けて、そのとき塗っている
スロットに問い合わせる。`mouseenter`/`mouseleave` も同様に `mousemove` へ寄せた。

## 収集の「未取得」判定も manifest を見る

`collect.py` は当初、未取得スライスを `data/raw/` と `.miss` の有無だけで
決めていた。ところが `data/raw/` は `.gitignore` 済みなので、**CI では毎回空**。
窓の既定を3時間から120時間に広げた途端、**Actions を回すたびに窓のぶんを
丸ごと取り直す**ようになった。

| 窓 | 取り直す量 | 所要 |
|---|---:|---|
| 3時間（旧既定） | 36 スライス | 約30秒（無視できた） |
| 120時間（現在） | 1,441 スライス | **約15分＋気象庁へ1,441リクエスト** |

`archive/manifest.json` のビットマップを見るようにして、実測 1,441 → **3** に
なった（残る3件は本当にまだ取っていない直近ぶん）。

- **枠番は `slice_day_index()` を使う。** normalize.py が立てるビットと同じ
  数え方でないと1枠ずれ、「毎回1スライスだけ取り直す」壊れ方をする。
- raw / `.miss` の有無も併せて見る。これは「取ったが normalize 前」を
  二重取りしないための補助であって、判定の一次情報ではない。
- `--refetch` で manifest を無視して取り直せる。ビットマップを疑うときの逃げ道。
- **安全性の根拠は normalize.py が既存アーカイブとマージすること。**
  `load_archive()` して `update()` するので、collect が新しいスライスしか
  持ってこなくても既存の件数は減らない。ここが上書き実装だったら、
  この最適化はアーカイブを壊していた。

突き合わせで確認したこと（実データ 1,441 スライス）:

- ビットマップの `1` の数と manifest の `slices` が全日で一致
- `archived()` の判定数とビットマップ直読みの数が一致（1,438）
- 枠番が 0..287 に収まり、窓内で衝突しない
- JST 00:00 終端が前日の枠287 に入る（`slice_day_index` の定義どおり）

## 標準コントロールは参考実装に合わせる

配置は `japan-gtfs-frequency-converter`（`viewer/src/main.ts`）に揃える。
ズームと現在地は**右上**、縮尺は左下、出典は `compact` で右下。
当初ズームだけ右下に置いていたが、参考実装と食い違っていた。

- **`attributionControl: false` を Map のオプションに入れてから**
  `AttributionControl({ compact: true })` を足す。切らずに足すと出典が2つ並ぶ。
- 出典は compact にしても消えない（ⓘ で開く）。気象庁の出典はパネル脚注にも
  別途出しているので、どちらか一方が隠れても要件は満たす。

### ダークテーマでアイコンが埋もれる

**MapLibre 標準アイコンは `fill='#333'` 固定。** `.maplibregl-ctrl-group` の
背景だけ `--surface-solid` でダークにすると、＋と−が暗い面に埋もれて
「かすれて見えない」になる（実際にそう見えていた）。背景を差し替えたら
アイコン側も必ず面倒を見ること。

```css
:root[data-theme='dark'] .maplibregl-ctrl-group button .maplibregl-ctrl-icon {
  filter: invert(1) hue-rotate(180deg);
}
```

**`invert(1)` だけにしない。** 現在地アイコンは追従状態で色が付く（青など）ので、
反転しただけだと色相が反転して別の色になる。`hue-rotate(180deg)` で戻す。

区切り線（既定 `#ddd`）も忘れない。暗い面に白線が走って浮く。ホバーの
`rgb(0 0 0/5%)` も暗い面では見えないので `--hover` に寄せる。

## 公開サイトが更新されないときはブラウザのキャッシュを疑う

Actions を回して収集もタイル生成も gh-pages デプロイも成功しているのに、
**ビューアの日付タブに新しい日が出ない**ことがある。原因はサーバではなく
ブラウザのキャッシュだった。

GitHub Pages は静的ファイルに `Cache-Control: max-age=600` を返す。
ところがこのパイプラインの出力は**ファイル名が固定なのに中身が変わる**:

| URL | いつ変わるか |
|---|---|
| `pmtiles/index.json` | 収集するたび（日付一覧そのもの） |
| `pmtiles/liden_YYYYMMDD.pmtiles` | 同じ日を追加収集するたび（枠が増える） |

そのため対策を入れないと 10 分間は古いものが出続ける。実際の切り分け方は
「公開中の `index.json` を curl して新しい日付が入っているか見る」。
入っていればサーバは正しく、疑うのはブラウザ側。

- **`index.json` は `fetch(..., { cache: 'no-store' })` で必ず取りに行く。**
  索引は数 KB なので毎回取っても問題にならない。
- **PMTiles は URL に版数を付ける**（`?v=<slices>-<bytes>`）。こちらは
  数 MB あるので `no-store` にはできない。`build.py` が書く実測値なので、
  中身が変わったときだけ URL が変わり、変わらない日はキャッシュが効いたままになる。
  デプロイ時刻のような全日共通の値にすると、1日ぶん増えただけで全日を
  再ダウンロードさせてしまう。
- **PMTiles でキャッシュが混ざるのは「古い」より悪い。** レンジ取得なので
  ヘッダ／ディレクトリだけ古いキャッシュから来るとオフセットがずれ、
  「地図は出るが落雷が出ない・欠ける」形で壊れる。
- **クエリを足しても pmtiles の Protocol は壊れない。** タイル URL の解析は
  `/pmtiles:\/\/(.+)\/(\d+)\/(\d+)\/(\d+)/` の**貪欲**マッチなので、
  `/` を含まないクエリ（`?v=155-438839`）は末尾の z/x/y と取り違えられない。
- 検証に `python -m http.server` を使うと**Range 非対応で 206 を返さない**ため、
  `Server returned no content-length header ...` が出る。これはサーバ側の
  制限であってビューアの不具合ではない。Range を返すサーバで確かめる。
