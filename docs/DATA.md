# データ仕様（実測記録）

気象庁ナウキャストの `liden`（落雷の位置）について、実際に叩いて確かめた挙動と、
一次資料で裏を取った定義。**再調査の手間を省くための記録**なので、数値は
すべて測った日付つきで残している。

利用方法は [README](../README.md)、実装の設計判断は [DESIGN.md](DESIGN.md)。

## 配信の保持期間は約5日

これがこのリポジトリの設計をほぼ全部決めている。

`data.geojson` の URL は basetime を直接指定できるが、**約5日より古い basetime は
404 になる**。実測（2026-08-23 02:35 UTC 時点）:

| basetime (UTC) | 現在からの経過 | HTTP |
|---|---|---|
| `20260822233500` | 3時間前（`targetTimes_N3.json` の最古） | 200 / 55件 |
| `20260820023500` | 3日前 | 200 / 36件 |
| `20260818023500` | 5日前 | 200 |
| `20260817203500` | 5日6時間前 | **404** |
| `20260815000000` | 8日前 | **404** |
| `20240807070000` | 2年前 | **404** |

`liden` を列挙するのは **`targetTimes_N3.json`**（43件・約3.5時間）で、
`N1` / `N2` は高解像度降水ナウキャスト（`hrpns`）だけで liden を含まない。
N3 の `elements` は `amds_rain10m` / `liden` / `slmcs` / `thns` / `trns` など。

いずれにせよ、列挙されるのは直近3〜3.5時間だけだが URL を直接叩けば約5日前まで
生きている。**列挙されている範囲＝取得できる範囲ではない。**

ここから出てくる帰結:

- **過去への遡り取得はできない。** 収集していなかった期間は永久に埋まらない。
  「あの日の落雷を見たい」は、その日に収集していなければ叶わない。
- **逆に、5日以内なら後から埋められる。** だから 5 分ごとに cron を回す必要はない。
  「窓の中で未取得のスライス」をまとめて取れば取りこぼさない。
- **`archive/` に入るまでデータは恒久化していない。** `data/raw/` は
  「同じスライスを二度取らない」ためだけのキャッシュで、いつ消してもよい。
  一次資産は `archive/liden_YYYYMMDD.geojson.gz`（コミット対象）。

この制約を踏まえた運用方針（定期収集をしない理由と代償）は
[README](../README.md#いちばん大事な制約配信は約5日で消える) にある。

## データの前提（実測で確認済み）

`scripts/collect.py` の `validate_slice()` がこれらを毎回検査し、崩れたら警告する。
黙って通すと配信側の仕様変更に気づけない。

- **basetime は UTC の5分境界。** 1スライスは `(basetime - 5分, basetime]` の観測を含む。
  2026-08-22 06:30〜08:25 UTC の連続24スライス・2,466件で、範囲外の `obstimeJST` は
  **0件**。
- **スライス間に重複はない。** 同じ24スライスで `id` も `(obstimeJST, 座標, type)` も
  2,466/2,466 がユニーク。5分バケットは互いに素。
  （それでも `normalize.py` は `src_id` で重複排除する。再取得や再送で二重に
  入る余地は残るので、冪等にしておく。）
- **geometry は Point のみ。** properties は `id` / `obstimeJST` / `type` の3つだけ。
- **`obstimeJST` はミリ秒まで入る**（`2026/08/22 16:35:00.010`）。JST。
- **座標精度は小数3桁**（約100m）。同24スライスで 3桁が 4,461・2桁が 416・1桁が 55。
  4桁以上は出ない。→ [タイルの最大ズームがこれで決まる](DESIGN.md#設計上の決めごと)。
- **1スライスの件数は活発時で 40〜180件。** 2026-08-21（JST）は1日で 23,639 件。

## 放電種別（`type`）とは

配信される `type` は **0 / 1 / 4** の3値（実測: 2,466件で 0=1,085 / 4=990 / 1=391）。
意味は気象庁の一次資料に定義がある。

### 気象庁による定義

> **A）放電種別について**
>
> 雷放電は、大きく分けて**雲放電**（雷雲の中や雲と雲の間で起きる放電）と
> **対地放電**（雷雲と大地の間の放電で、落雷ともいう）の二種類があります。
> それぞれの雷放電から発する電磁波の特徴が異なることを利用してこれらを区別しています。
>
> — 気象庁「配信資料に関する仕様 No.13201 雷観測データ」
> （[PDF](https://www.data.jma.go.jp/suishin/shiyou/pdf/no13201)）

| 種別 | 定義 | `type` | 別名 |
|---|---|---:|---|
| **雲放電** | 雷雲の**中**や、**雲と雲の間**で起きる放電 | 0, 1 | CC（Cloud-to-Cloud） |
| **対地放電** | **雷雲と大地の間**の放電 | 4 | **落雷**。CG（Cloud-to-Ground） |

コード対応の根拠は同仕様の別紙（第1放電データ）:

```
72～73  UINT2  MMTT   雷多重度（MM）：0 ≦ MM ≦ 99
                       後続雷撃の数（但し、雲放電の場合は 0）
                       放電種別（TT）：0-1 雲放電、4 対地放電
```

**「落雷」は対地放電（type 4）だけを指す。** 雲放電は空中で完結する放電なので、
地上への落雷ではない。「落雷だけ見たい」ならビューアで雲放電のトグルを切る。

雲放電が 0 と 1 の2値に分かれる理由は同仕様では説明されていない（どちらも雲放電）。
気象庁のナウキャスト表示も `CG.svg` / `CC.svg` の2アイコンしか持たないので、
表示上も2種として扱われている。

### 雷多重度（このデータには入っていない）

同仕様には雷多重度の定義もあるが、**ナウキャストの GeoJSON には含まれない**
（properties は `id` / `obstimeJST` / `type` の3つだけ）。多重度が必要なら
[公式アーカイブ](#5日より前の落雷が欲しいとき)を購入することになる。

> **B）雷多重度について**
>
> 雲放電や対地放電の放電開始から終了までの一連の放電過程のことを、
> **雷光（フラッシュ）** と呼びます。また、対地放電は**雷撃（ストローク）**とも
> 呼びます。対地放電での一連の放電過程（雷光）においては雷撃が連続して発生することが
> あり、最初の雷撃を**第一雷撃**、それに続くものを**後続雷撃**と呼びます。
> 配信するデータでは、後続雷撃の数を雷多重度としており、第一雷撃から後続雷撃を含めて
> 一つの放電データになります。
>
> — 同仕様 A)B) より

つまり **1レコード = 1雷光（フラッシュ）** で、対地放電の複数回の雷撃は
1レコードにまとめられている。**「type 4 の件数」は落雷回数（雷撃数）ではなく
落雷フラッシュ数**である点に注意。

### 標定の限界（気象庁の注意事項）

LIDEN は雷の電磁波（LF帯）の到達時刻差から位置を求めるので、原理的な限界がある。
同仕様「６．利用上の注意」より要点:

- **誤標定・位置誤差がありうる。** 雷放電以外の電磁波を使ってしまうことが理論上あり、
  逆に標定されないこともある
- **検知局から遠いほど精度が落ちる。** LF帯は到達距離が長いため日本列島沿岸から
  遠く離れた領域にも標定されるが、精度は距離とともに低下する
  （このリポジトリのデータでも太平洋上や大陸寄りに点が出ることがある）
- **1分間に5万件を超えると超過分は配信されない**（1電文500KBの制約）。
  参考値として気象庁は「2016年は8月2日の1分間で749件が最大」と記している
- 検知局1〜2局の障害では標定に支障はないが、大規模障害時のデータは**再配信されない**

### このリポジトリでの扱い

**アーカイブは `type` を変換しない。** ラベル付けはビューア側
（`viewer/src/layers.ts` の `DISCHARGE_GROUPS`）だけで行う。
仕様が改訂されてもアーカイブを作り直さずに済むし、一次資料に無いコードが
現れても取りこぼさない:

- `collect.py` は `0 / 1 / 4` 以外の `type` を見つけたら警告する
- ビューアは未知のコードを「その他（仕様に無いコード）」に集める。**黙って隠さない**

## 5日より前の落雷が欲しいとき

この配信からは取れない。**別ルートで買う。**

| 経路 | 遡れる範囲 | 形式・備考 |
|---|---|---|
| このリポジトリ（ナウキャスト配信） | **約5日** | 無料・GeoJSON。`type` はあるが**雷多重度は無い** |
| [気象業務支援センター](http://www.jmbsc.or.jp/) | **2017年1月〜** | 公式アーカイブ。オンライン配信ではなく都度取り寄せ。年月日時分秒・緯度・経度・雷多重度・放電種別 |
| [日本気象「雷観測データ」](https://ods.n-kishou.co.jp/data/detail/513) | **2017年6月1日〜** | バイナリ／CSV。過去データ配信あり（要契約）。CSV は緯度20〜48°・経度118〜150°の任意領域 |
| [ハレックス DreamAPI 雷実況](https://www.halex.co.jp/service/api3/17048-2.html) | 直近中心 | API。`type` の定義はこの仕様書で公開されている |

「LIDEN」は **雷監視システム（LIghtning DEtection Network system）** の略で、
全国30か所の検知局と東京の中央処理局で雷の電磁波を受信し、発生時刻・位置・
放電種別を標定するシステム。ナウキャストの `liden` レイヤはその出力の一部を
無料で流しているにすぎない。**多重度つきの完全なデータや、5日より前の期間が
必要なら支援センター経由になる。**
