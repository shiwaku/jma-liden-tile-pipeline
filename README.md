# jma-liden-tile-pipeline

気象庁の高解像度降水ナウキャスト「落雷の位置」（liden）を 5分スライス単位で取得し、
JST 日別のアーカイブにまとめて **PMTiles** を生成し、MapLibre のタイムラプスビューアで見る。

**雷雨のときに手で叩いて最新を見る**運用（定期収集はしない）。理由と代償は
「運用方針」を参照。

- 出典: 気象庁 高解像度降水ナウキャスト（落雷の位置）
- ライセンス: 気象庁ホームページ利用規約（出典明示で利用可）
- 姉妹リポジトリ: [`jma-liden-on-kepler`](https://github.com/shiwaku/jma-liden-on-kepler)
  — 2024/08/07 の6時間ぶんを kepler.gl で1回だけ可視化したもの。**あちらのデータは
  もう取得できない**（下記の保持期間を参照）。このリポジトリは同じことを
  再現可能な形で、いつでもやり直せるようにしたもの。

## 最初に知っておくべきこと：配信は約5日で消える

これがこのリポジトリの設計をほぼ全部決めている。

`data.geojson` の URL は basetime を直接指定できるが、**約5日より古い basetime は
404 になる**。実測（2026-08-23 02:35 UTC 時点）:

| basetime (UTC) | 現在からの経過 | HTTP |
|---|---|---|
| `20260822233500` | 3時間前（`targetTimes_N1.json` の最古） | 200 / 55件 |
| `20260820023500` | 3日前 | 200 / 36件 |
| `20260818023500` | 5日前 | 200 |
| `20260817203500` | 5日6時間前 | **404** |
| `20260815000000` | 8日前 | **404** |
| `20240807070000` | 2年前 | **404** |

`targetTimes_N1.json` が列挙するのは直近3時間（37件）だけだが、URL を直接叩けば
約5日前まで生きている。**列挙されている範囲＝取得できる範囲ではない。**

ここから出てくる帰結:

- **過去への遡り取得はできない。** 収集していなかった期間は永久に埋まらない。
  「あの日の落雷を見たい」は、その日に収集していなければ叶わない。
- **逆に、5日以内なら後から埋められる。** だから 5 分ごとに cron を回す必要はない。
  「窓の中で未取得のスライス」をまとめて取れば取りこぼさない。
- **`archive/` に入るまでデータは恒久化していない。** `data/raw/` は
  「同じスライスを二度取らない」ためだけのキャッシュで、いつ消してもよい。
  一次資産は `archive/liden_YYYYMMDD.geojson.gz`（コミット対象）。

## 運用方針：溜めない。雷雨のときに最新を見る

**このリポジトリは定期収集をしていない。** cron も常駐もタスクスケジューラも無く、
`.github/workflows/collect.yml` は手動実行専用にしてある。

雷雨に気づいたら叩く:

```powershell
.\refresh.ps1              # 直近3時間を取って、タイルを作って、ビューアを開く
.\refresh.ps1 -Hours 12    # 直近12時間
.\refresh.ps1 -NoViewer    # 取得とタイル生成だけ
```

```bash
python scripts/refresh.py --hours 3   # ↑の中身（collect → normalize → build）
```

直近3時間は 36 スライスで **約30秒**。4日ぶん（1,153スライス）だと 13 分ほど。

**この選択の代償をはっきり書いておく:**

- **走らせなかった期間のデータは永久に失われる。** 「先週の雷雨」は取れない。
  それを承知の上で、常時収集のコストを払わない側に振っている。
- **気づいてから5日以内なら遡れる。** 「昨日の夕方すごかった」は `--hours 48`
  で拾える。雷雨の翌日に思い出しても間に合う。
- 継続的に溜めたくなったら `collect.yml` の `schedule` のコメントを外す
  （6時間ごと）。`archive/` が1日あたり 1〜3 MB 増える。

## データの前提（実測で確認済み）

`scripts/collect.py` の `validate_slice()` がこれらを毎回検査し、崩れたら警告する。
黙って通すと配信側の仕様変更に気づけない。

- **basetime は UTC の5分境界。** 1スライスは `(basetime - 5分, basetime]` の観測を含む。
  2026-08-22 06:30〜08:25 UTC の連続24スライス・2,466件で、範囲外の `obstimeJST` は
  **0件**。
- **スライス間に重複はない。** 同じ24スライスで `id` も `(obstimeJST, 座標, type)` も
  2,466/2,466 がユニーク。5分バケットは互いに素。
  （それでも `normalize.py` は `src_id` で重複排除する。再取得や再送で二重に
  入る余地は残るので、冪等にしておく。）
- **geometry は Point のみ。** properties は `id` / `obstimeJST` / `type` の3つだけ。
- **`obstimeJST` はミリ秒まで入る**（`2026/08/22 16:35:00.010`）。JST。
- **座標精度は小数3桁**（約100m）。同24スライスで 3桁が 4,461・2桁が 416・1桁が 55。
  4桁以上は出ない。→ タイルの最大ズームがこれで決まる（後述）。
- **1スライスの件数は活発時で 40〜180件。** 2026-08-21（JST）は1日で 23,639 件。

### `type` は解釈せず素通しする

`type` は **0 / 1 / 4** の3値を観測している（2,466件で 0=1,085 / 4=990 / 1=391）。

気象庁のナウキャスト表示は `CG.svg`（Cloud-to-Ground = 対地放電）と
`CC.svg`（Cloud-to-Cloud = 雲放電）の2つのアイコンを持っているので、
表示上は少なくとも2種を区別している。だが **数値コードとの対応は一次資料で
確認できていない**:

- 配信 JS（`jmatile.bundle`・`jmatile.utility.bundle`）に `CG` / `CC` / `liden`
  の文字列が無い。レイヤ定義が JSON に露出していない。
- `jma.go.jp/jma/kishou/know/kurashi/thunder.html` と `bosai/nowc/help.html` は 404。

アイコンは2種、コードは3値なので 1:1 でもない。**推測した対応をデータに焼き付けると
後から直せない**ので、`normalize.py` は `type` を変換せずそのまま通し、
ビューアも「type 0 / 1 / 4」と配信値のまま並べる。
対応が一次資料で確認できたら、その時にラベルを足せばよい。

## パイプライン

```
data/raw/YYYY/MM/DD/liden_<basetime>.json   ← collect.py    5分スライス（キャッシュ・gitignore）
archive/liden_YYYYMMDD.geojson.gz           ← normalize.py  JST日別の恒久アーカイブ（コミット）
archive/manifest.json                       ← normalize.py  288枠のカバレッジ
dist/liden_YYYYMMDD.pmtiles + index.json    ← build.py      ベクタータイル（gitignore）
```

```bash
python scripts/refresh.py     # ↓の3つをまとめて（雷雨のとき叩くのはこれ）
python scripts/collect.py     # 窓の中の未取得スライスを取る
python scripts/normalize.py   # raw -> archive/
python scripts/build.py       # archive/ -> dist/*.pmtiles
python scripts/status.py      # 収集カバレッジの点検
python scripts/prune.py       # 取り直せない古い raw キャッシュを消す（--apply で実行）
```

`make` があれば `make refresh`（`HOURS=12` で変更可）／`make status` など。
Windows の Git Bash には `make` が無いので、その場合は上の `python` を直接使う
（`refresh.ps1` が PowerShell からのいちばん短い入口）。

### 空スライスも保存する

雷が無かった5分も `{"type":"FeatureCollection","features":[]}` として保存する。
**「取得済みで雷なし」と「未取得」を区別できないとカバレッジが検証できない。**
初回の4日ぶん1,153スライスのうち87スライスが空だった。

404（配信終了）は `.miss` マーカーを残し、以後試行しない。

### カバレッジの見方

`status.py` は5つに分ける。**まだ取れるものと、もう取れないものを混ぜない**のが要点。

```
JST 日付      取得済    欠落    窓外  期限切  配信終    合計   落雷件数
2026-08-19       148     140       0       0       0     288      1,256
2026-08-20       288       0       0       0       0     288     17,055
2026-08-21       288       0       0       0       0     288     23,639
```

| 区分 | 意味 |
|---|---|
| 取得済 | `manifest.json` のカバレッジに立っている（空スライス含む） |
| 欠落 | 収集窓の中で未取得 → `collect.py` をそのまま回せば埋まる |
| 窓外 | 収集窓より古いが配信保持期間の中 → `--window-days 5` で **まだ取れる** |
| 期限切 | 配信保持期間より古く未取得 → **もう取れない** |
| 配信終 | 404 を確認済み |

判定は `data/raw/` の有無ではなく **`manifest.json` のカバレッジ**を見る。
raw はいつ消してもよいキャッシュなので、raw を基準にすると掃除した瞬間に
「欠落」が復活してしまう。

## 設計上の決めごと

- **日別の区切りは JST。** basetime は UTC だが観測時刻は JST で配信される。
  日本の落雷を日単位で見るのは JST が自然なので、アーカイブとタイルは JST 日付で切る。
  1つの JST 日は UTC 15:00(前日)〜15:00 の basetime にまたがる。
  - スライスの枠番は「JST 00:05 終端 = 枠0」「翌 00:00 終端 = 枠287」と定義し、
    日 D の枠 0..287 が obstime `(D 00:00, D+1 00:00]` をちょうど覆うようにしている。
  - **features の日付は常に obstime が決める。** 境界の一瞬（obstime がちょうど
    `00:00:00.000`）だけ、枠のカバレッジと1件だけ食い違う余地がある。実害はないが仕様。
- **配信元の `id` を一次キーにしない。** `nowc_<basetime>_<validtime>_liden_<連番>` の
  連番はスライス内の並び順に依存する。時刻・位置・種別を一次情報として持たせ、
  `src_id` は出所と重複排除のためだけに残す。
- **`epoch_ms` を持たせる。** MapLibre の filter は数値比較が軽く、時間スライダーに
  そのまま使える。文字列の時刻だけだと絞り込みが書きづらい。
- **最大ズームは 7。** 元データの座標精度が 0.001 度なので、タイル解像度が
  精度に達する ZL は `360/(4096×2^z) ≤ 0.001` → `z ≥ 6.5` → **z7**。
  それ以上は情報を増やさず、同じ点を多くのタイルに複製するだけ。実測（2026-08-21・
  20,271件）:

  | 最大ZL | PMTiles サイズ | 最大ZLの一意 `src_id` |
  |---:|---:|---:|
  | 6 | 2.12 MB | — |
  | **7** | **2.71 MB** | **20,271** |
  | 8 | 3.34 MB | — |
  | 10 | 4.75 MB | — |
  | 12 | 6.68 MB | 20,271 |

  z7 と z12 で最大ZLの一意 `src_id` が **完全一致**（どちらも欠落なし）。
  容量は 59% 減る。高ズームはビューア側のオーバーズームで描く。
- **`-r1` で点の間引きを止める。** 落雷は1点1事象なので落とさない。低ZLの過密だけ
  `--drop-densest-as-needed` に任せる（見た目の問題で、最大ZLの件数には影響しない）。
- **内容が変わらなければアーカイブを書かない。** 書き直すと mtime が動き、
  `build.py` が「入力が新しい」と見て全日のタイルを作り直す。`write_archive()` が
  バイト列を比較して `SAME` を返す。
  - バイト列を一致させるには **`mtime=0` だけでは足りない。**
    `gzip.GzipFile(fileobj=開いたファイル)` は fileobj の `.name` を gzip ヘッダの
    FNAME に埋めるので、同じ内容でもバイト列が変わる。`io.BytesIO` に書けば付かない。

## 実行環境

- Python 3.12（標準ライブラリのみ。収集・正規化に外部パッケージは不要）
- tippecanoe 2.80 / pmtiles 1.30（タイル生成のみ）
- Node.js 20+（ビューアのみ）

### tippecanoe が WSL 側にしか無い場合

`build.py` は自動で切り替える:

1. PATH に `tippecanoe` があればそのまま実行（Linux・CI・WSL 内）
2. 無ければ `wsl.exe` 経由で実行し、パスを WSL 形式に変換して渡す

パス変換はリポジトリ直下を一度だけ `wslpath` で引いて相対パスを繋ぐ。
`/mnt/c` 固定を前提にしない。

### tippecanoe は `.pmtiles` を指定しても mbtiles を書く

2.80 で確認（先頭バイトが `SQLite format 3`）。`build.py` は出力の
**マジックバイトを見て判定**し、SQLite なら `pmtiles convert` を通す。
既に PMTiles ならそのまま使う。バージョンによって挙動が違うので、
拡張子でもバージョン番号でもなく中身で判断する。

## ビューア (`viewer/`)

Vite + TypeScript + MapLibre。背景は国土地理院の最適化ベクトルタイル（淡色）で、
ダーク／ライト切替に対応する。

```bash
cd viewer
npm install
npm run dev       # 開発サーバー（http://localhost:8000/ 。使用中なら 8001, 8002... と繰り上がる）
npm run build     # 本番ビルド -> viewer/dist/
```

- 開発サーバーはリポジトリ直下 `dist/` の PMTiles を `/pmtiles` から
  **Range(206) 対応**で配信する（`vite.config.ts` のミドルウェア）。
  先に `python scripts/build.py` でタイルを作っておく。
- 本番配信では PMTiles を置いた URL を `viewer/.env` の `VITE_PMTILES_BASE` に指定する。
- `make deploy-pages` でビューアをビルドし、`dist/` の PMTiles を同梱して
  `gh-pages` ブランチへ force push する。

### できること

- **日付切替**（`dist/index.json` から自動生成）。未取得の時間帯がある日は
  下線を破線にして、件数と `枠/288` を出す。**欠けている日を欠けていないように
  見せない。**
- **タイムラプス再生**。5分刻みの288枠を進める。速度は 2 / 5 / 15 分/コマ。
- **残光**（表示する直前の時間）5分〜3時間、または1日ぶんすべて。
  残光モードでは経過時間で色が変わる（白→黄→橙→赤紫）ので、同じ場所に
  重なった古い点と新しい点が区別できる。
- **`type` フィルタ**（配信値のまま）
- クリックで1件の `obstime` / `type` / 配信スライスを表示

### ビューア実装で踏んだこと

- **`['literal', '#ffc247']` を色として渡さない。** `literal` は配列・オブジェクト
  専用なので色式として不正で、**レイヤーの paint が丸ごと無効になる**。しかも
  `map.on('error')` に何も出ず、`console.error` にも出ない。症状は
  「点は薄く出るが背景地図が真っ白」という一見無関係な壊れ方だった。
  経過時間で色を分けないときは **素の色文字列**を返す。
- **`queryRenderedFeatures` はタイル読み込み前は空を返す。** `setFilter` の直後に
  数えると常に 0 件になる。`map.on('idle')` で数え直す。
- **`queryRenderedFeatures` は同じ点をタイル境界で二重に返す。** 件数は `src_id` で
  数え直す（実測: 生の配列 21,412 に対し一意 20,271）。
- **背景地図が `pmtiles://` なので、`maplibregl.addProtocol('pmtiles', ...)` は
  落雷タイルと無関係に必須。** 外すと背景が出ない。
- ビューアを変えたら実際に描画とクリック読み取りを確認する。タイルURLや式の不整合は
  「地図は出るがオーバーレイだけ出ない」形で静かに壊れる。

## 初回収集の実績

2026-08-23 に4日窓で初回収集した結果:

| JST 日付 | 落雷件数 | 枠 | PMTiles |
|---|---:|---:|---:|
| 2026-08-19 | 1,256 | 148/288 | 0.20 MB |
| 2026-08-20 | 17,055 | 288/288 | 2.30 MB |
| 2026-08-21 | 23,639 | 288/288 | 3.05 MB |
| 2026-08-22 | 8,054 | 288/288 | 1.08 MB |
| 2026-08-23 | 3,215 | 141/288 | 0.42 MB |

1,153スライス取得（うち空87）／落雷 53,219 件／404 は0件。
完全な日は 1 日あたり 1〜3 MB 程度で、**1年ぶん溜めても 1 GB に届かない**。
